# 风险检查细则与 License 商用结论表

> 用于第七节「风险与注意」。结论一律**只写证据**，不写价值判断；读不到的写「未验证」。

## 1. License 商用结论表

| License | 商用 | 修改 | 闭源分发 | 主要义务 | 提示语 |
|---|---|---|---|---|---|
| MIT | ✅ | ✅ | ✅ | 保留版权与许可声明 | 「随便用，留个版权声明即可」 |
| Apache-2.0 | ✅ | ✅ | ✅ | 保留声明 + NOTICE + **专利授权条款** | 「可商用，注意保留 NOTICE」 |
| BSD-2/3 | ✅ | ✅ | ✅ | 保留声明；3 条款禁用人名背书 | 「可商用，别用作者名字做宣传」 |
| MPL-2.0 | ✅ | ✅ | ✅（同文件需开源） | **文件级** copyleft | 「改到它的文件就要开源那一份」 |
| LGPL | ✅ | ✅ | ⚠️ 动态链接通常可以 | 库本身改动需开源 | 「当库用没事，改它本体要注意」 |
| GPL-2.0/3.0 | ✅ | ✅ | ❌ 分发衍生作品须开源 | 传染性强 | 「自己用没事，对外分发要开源」 |
| **AGPL-3.0** | ✅ | ✅ | ❌ | **网络服务也算分发** | 「**做 SaaS 要特别小心：只要联网提供给它，就要开源你的改动**」 |
| 无 License | ❌ | ❌ | ❌ | 默认「保留所有权利」 | 「**没写许可证 = 不能随便用**，仅供阅读学习」 |
| 自定义 / 双许可 | ⚠️ | ⚠️ | ⚠️ | 逐条读 | 「条款非标准，需自行确认，本条未验证」 |
| Unlicense / CC0 | ✅ | ✅ | ✅ | 无 | 「等同公有领域」 |

补充规则：

- License 字段来自 Search API 的 `license.spdx_id`；为 `null` 时**不等于没有**——要去读 `LICENSE` 文件确认，读不到就写「未验证」。
- **AGPL 与「要不要自建服务」联动**：若项目是 AGPL 且推荐语里写了"自己部署给团队用"，必须补一句传染性提示。
- 「能商用」≠「可以拿它的输出商用」：模型权重、数据集、商标是另一回事，遇到时单独标注。

## 2. 风险等级判定表

| 等级 | 判据（满足其一即算） | 典型信号 |
|---|---|---|
| **低** | 本地小工具、无敏感权限、MIT/Apache、近 30 天有提交 | 单文件 CLI、`pipx`/`npx` 即装即用、不联网 |
| **中** | 需 token / 联网 / 依赖多 / 文档一般；或单一作者且 star 尚低 | 需要 API Key、需要自建后端、依赖 50+ 包、README 只有几行 |
| **高** | 要 root 或管理员权限、执行未知脚本、无 License、上传敏感数据、金融/医疗/安全场景 | `curl \| bash` 安装、Docker `--privileged`、要求把代码/文件上传到第三方 |

判定纪律：

- 信息不足时**按最保守取值**（读不到 License → 至少「中」；要 root 且无 License → 「高」）。
- 「低」不能因为 star 高就给，**star 不是风险维度**。
- 等级必须写进条目，**并且**给出依据短语（如「低：本地 CLI、MIT、3 天前有提交」），不能只写一个「低」。

## 3. 逐项检查表（八项，逐条给结论）

| 项 | 要答的问题 | 数据来源 |
|---|---|---|
| 安全 | 要 root 吗？执行脚本吗？带二进制吗？要上传文件吗？有挖矿/后门嫌疑吗？ | README + 安装脚本 + Release 资产 |
| 法律 | 哪个 License？能商用吗？ | `license.spdx_id` + `LICENSE` 文件 |
| 隐私 | 收遥测吗？要登录吗？会把代码传出去吗？ | README 的 Privacy 段 + 配置项 |
| 维护 | 最近提交多久？Issue 有人管吗？单人项目吗？归档了吗？ | `pushed_at` + `archived` + Issues/PR 数 |
| 成本 | 要 API 费、云服务器、数据库、存储吗？ | README 的 Setup/Cost 段 |
| 使用 | 会破坏数据吗？生产能用吗？有 breaking changes 吗？ | Release notes |
| 供应链 | 依赖多少？有 lock 文件吗？版本 pin 了吗？ | 仓库文件列表（`package-lock.json`、`uv.lock`、`go.sum`） |
| 社区 | 刷星吗？营销味重吗？有争议吗？ | fork/star 比、release 记录、issue 讨论 |

**刷星快速判据**（与 `RUBRIC.md` 第 1 节一致）：`fork/star < 0.02` **且** 无 release **且** 无 issue 讨论 → 命中则淘汰，不进推荐区；只有其中一两条则降权并在条目里注明。

## 4. 数据冲突优先级

1. **Release / Issues**（客观、有日期）> 2. 仓库 `description` > 3. README 自述 > 4. 作者在别处的宣传。
冲突时以高优先级的为准，并在条目里写一句「README 称 X，但 Release 显示 Y」。**不要把 README 的营销文案当事实抄进日报。**

## 5. 隐私与输出约束

日报与短版推送中**不得出现**：`GITHUB_TOKEN` 值、私有仓库名称、本机绝对路径、账号密钥、服务器 IP、以及用户在本地给该仓库打的私有备注（`note` 字段中若含个人评价，转述时去掉私人信息）。
